# Web 端响应与取流速度调查

2026-10-05，Claire 本机。用户确认电视从首页「点播」进入；后续以这一路为对照。没有取得电视或 Ethan Mac 的同步取流记录，不能把本机结果直接当作两台设备的实测结论。

## 已定位并修复：所有原生网络请求在同一线程排队

原实现把 `icSearch`、`icStaticDecode`、`icBigFile` 放在 `Java.perform()` 的 Promise 中。Promise 并没有把同步 JNI 网络调用移到后台线程。Node 即使使用 `Promise.all()`，请求也在 Frida 的同一线程依次执行。浏览器一次加载多张海报，会把搜索、选集和播放控制一起堵住。

这能解释「不只是下载，几乎所有操作都慢」的重要一部分，不能单独解释持续取流的吞吐。

修复：

- `agent-workers.js` 使用真正的 Java executor；元数据、海报分别使用两个工作线程，海报不能占用元数据队列，控制 RPC 不再等待图片下载。
- `agent-src.js` 的两套搜索、详情和海报 RPC 接入工作线程；同步更新编译产物 `agent.js`。
- 关闭引擎时取消排队任务、等待运行中的 JNI 调用结束，再 detach Frida，避免后台 Runnable 访问已卸载的脚本。
- 本机 launchd 的旧配置 `IDLE_MS=90000` 改为仓库当前默认的 `3600000`。这是本项目的模拟器保活时间，减少关页 90 秒后再次访问的冷启动。

### 实测对照

| 场景 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 冷缓存双目录搜索 `HS` | 5,271 ms | 2,684 ms |
| 8 张未缓存海报加载期间，读取频道 | 20,517 ms | 135 ms |
| 同上，读取 Silo 第三季选集 | 23,029 ms | 2,399 ms |
| 缓存命中的搜索 | 67 ms | 2 ms |

两轮搜索返回字节数相同，选集也为同一资源。海报均取 8 张未缓存图片，前后使用不同图片以避免命中已写入的磁盘缓存；这不是相同图片逐字节的网络基准。

线程独立检查：两个各 1,200 ms 的任务，旧实现串行完成约 2,400 ms，控制请求也等待约 2,400 ms。新实现约 1,286 ms 完成两个任务，控制请求约 23 ms 返回。关闭期间的八个测试任务均正常结束为取消/中断，原生 App 未退出。另做了真实海报请求中的服务重启检查，结果见 `restart-under-load.json`。

## 对持续吞吐的定位和限制

环球剧场在模拟器内直接读取原生 HTTP 输出时约 546 KiB/s。该路径绕过 ADB 视频转发、Node、宿主机 ffmpeg 和文件写入。因此，初轮约 600 KiB/s 已经存在于原生取流输出，不能归因于网页播放器或宿主机转码。

同步检查未显示宿主机 ffmpeg 算力不足；点播复制视频时 CPU 约 0–2.4%。离线同样的下载处理链路明显快于网络取流。服务端测速期间没有触发缓冲节流。

统计口径只作为辅助证据：APK 播放器显示的是全设备 `TrafficStats.getTotalRxBytes()` 的每秒增量，包含本地接口；项目下载面板显示实际文件增长。电视点播下载这一轮，同一模拟器的原生显示公式约为 4,858 KB/s，实际写入约 1,510 KiB/s。这不说明所有体验差距都只是数字，也不能从该比例推算用户电视上的有效吞吐。

还未定位清楚的部分：电视能在很短时间完成的首次搜索/选集，本机绕开排队后单次原生请求仍约 2 秒；电视点播初始供数和持续下载与电视真实链路的差别仍缺少同步证据。不能宣布“已达到电视速度”，也未证明 Ethan Mac 的剩余差距与 Claire 相同。

## 网络诊断记录与后续边界

只读检查发现：本机存在 Clash TUN，部分模拟器 UDP 请求经代理节点转发。此前做过进程 UDP 直连规则和指定淘星服务器 IP 的 TUN 旁路对照，并重载了配置。直连规则没有明显改善搜索；两轮旁路取流约 927 / 671 KiB/s，恢复原路径的一轮约 616 KiB/s，波动较大，不能认定代理是根因或把旁路保留为解决方案。

用户随后报告浏览器和 Codex 连接异常，重启 Clash 核心后恢复；用户与局域网另一台机器已核对配置与备份一致。异常具体内部原因尚未确定，不能擅自归因。临时修改模拟器 UDP 接收缓冲的试验未建立有效对照，已还原到原值，不据此作性能结论。

后续网络侧优先只读。未经用户明确确认，不修改 Clash 配置、TUN、系统代理、DNS、路由，也不重载或重启代理核心。如确有必要，必须先说明具体改动、可能影响的连接和回滚方式，并取得确认。

## 第二轮：优先保护持续播放

用户进一步明确经常遇到播放途中停下来等缓冲。本轮对网络配置保持只读，未改动 Clash、TUN、系统代理、DNS、路由，也未重载或重启代理核心。

### 默认片源与电视入口对齐

合并搜索原来把环球剧场固定放在同名多源节目的第一位，播放和加入下载队列随之默认使用这条链路。用户电视使用的是电视点播；同名节目在两套目录中对应不同的播放地址，Silo 第三季第八集的目录片长也分别为 3344 与 3395 秒。

为避免只按一集修改全局默认，补测了其他节目，各从第一集开头持续取流 35 秒，走当前完整服务链路，使用原生默认参数：

| 节目 | 环球剧场平均吞吐 | 电视点播平均吞吐 | 环球/电视首包时间 | 环球/电视最长供数间隙 |
| --- | ---: | ---: | ---: | ---: |
| Silo 第二季第一集 | 714 KiB/s | 1,858 KiB/s | 2.93 / 1.63 秒 | 4.53 / 1.18 秒 |
| 黄石第一季第一集 | 761 KiB/s | 2,144 KiB/s | 2.72 / 1.78 秒 | 3.15 / 0.72 秒 |

据此将**合并搜索中有两套来源的节目默认选择改为电视点播**，保留手动切换和环球剧场独有节目。Silo、黄石的实际搜索接口验证了新默认和仅有环球剧场资源的保留。这是选择与电视入口一致、在这些样本中供数更快的片源；两套资源的编码、码率可能不同，不能解释成同一文件的传输能力提高了相同比例，也不能保证所有节目均如此。

### 已部署的点播预缓存

此前服务端在浏览器已缓冲约 120 秒后暂停 ffmpeg 读取。这个门限可以控制浏览器内存，但也会停止继续储备视频。本轮在 ffmpeg 与浏览器之间加入最多 **256 MiB 的磁盘环形缓存**：

- 浏览器仍按约 100–120 秒待播内容控制投递；暂停时约 160–180 秒。
- 浏览器缓冲充足时，后台继续取流，直到额外磁盘缓存满；消费后自动补充。下载队列仍直接读取，不经过这份播放缓存。
- 以实际投递的 MPEG-TS PCR 时钟控制浏览器缓冲，避免把后台预取进度误当成已经送到浏览器的内容。
- 原生 App 退出或源断开时，保留同一 HTTP 响应和已经储备的内容，在后台恢复取流。预取需要补充且连续 20 秒没有数据时提前续接。
- 临时缓存文件创建后立即解除目录链接，关闭、切换播放或服务退出时释放。上限可通过 `VOD_BUFFER_MB` 调整，0 可退回原路径。

这一改动增加抵御供数波动的储备，没有改变源服务器的最大吞吐，也不等于消除了所有卡顿。改动前的一轮约六分钟测试没有复现中途卡顿，因此不能把原来的读取暂停单独认定为全部故障的根因。

### 实际播放与故障恢复

Silo 第三季第八集、电视点播，浏览器从约 10% 处恢复：

- 浏览器连续播放到相对进度 **673.6 秒**，最后 `readyState=4`，没有媒体错误或控制台警告。
- 连续 600 个一秒采样始终保持同一会话和 `alive=true`；其中客户端最低缓冲 90.9 秒。
- 测试中主动停止后台 Android 淘星 App（不是代理服务）。原生取流在 **17.9 秒**后恢复；18 个恢复中采样的最低客户端缓冲 **96.2 秒**，期间观察到播放进度持续前进。
- 磁盘缓存准确达到 **268,435,456 字节**上限，此后取流会背压，消费时补充。首次填满后又持续取得约 107 MiB，证明没有因满缓存而永久停取。
- 关闭测试页后服务恢复空闲，缓存文件和对应文件描述符均已释放。

随后重启项目服务加载最终代码，另做两倍速恢复测试：再次停止取流 App，18.0 秒后恢复，240 个一秒采样保持同一会话，最低缓冲 87.9 秒。首段结束点为相对时间 482.9 秒，浏览器实际播放超过该点至 569.3 秒，仍为 `readyState=4`、没有媒体错误或控制台警告。这轮验证了续接后的内容能够实际解码播放，不仅是故障期间继续消耗旧缓存。

通过真正的 `DownloadQueue` 隔离实例复测电视点播第八集，平均文件写入 **1,618 KiB/s**，测量结束时已写入 **106,692,656 字节**，取得约 394 秒媒体。该值不是相对本轮修改前的对照提升；它用于确认当前部署的真实下载吞吐以及下载没有被播放缓存限流。正式下载队列为空，下载目录保持不变，测试片段已删除。

## 第四轮：暂停十分钟后的续播

实际暂停《黄石》S1E3（电视点播）635.3 秒和 Silo S1E5（环球剧场）626.2 秒，续播的新可见帧分别为 60.9 与 95.2 毫秒。随后分别连续观察 265.3 与 253.5 秒，没有等待缓冲、解码错误、进度回退或会话重建。暂停结束时浏览器分别保留约 179.5 / 169.1 秒内容，磁盘预缓存约 256 / 102.7 MiB。

黄石续播后重新取得约 48.3 MiB 数据；Silo 在暂停期间已收到原生片尾通知，续播从保留的缓存继续读取。两轮均实际播放超过暂停结束时浏览器已有的内容，验证了后续缓存补入。

同时通过回归测试确认并修复了暂停意图丢失：后台网络恢复或转码回退不再让用户主动暂停的视频自行播放；解码器错误、换流和媒体结束导致的暂停也不会被误存为用户暂停。新增 11 项前端状态测试，项目全部 22 项测试通过。正常长暂停测试没有注入故障；异常恢复边界通过实际 UI 处理函数的隔离测试覆盖。

完整方法、范围和数据见 [暂停十分钟后续播验证](playback-pause-validation-2026-10-05.md)。测试期间页面保持打开、电脑未休眠，没有修改网络配置；结果不代替此前两个未解决播放问题的修复验证。

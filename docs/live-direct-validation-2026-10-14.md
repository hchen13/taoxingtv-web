# 2026-10-14：Golf HD 断流修复与本机直连验证

环境：Claire Mac，服务仍在 `claire-mini.local:8090`。本轮没有修改 Clash 配置、TUN、系统代理、DNS 或路由表，没有重载或重启代理核心。

## 已确认的问题

原页面的 Golf HD 停在 32.461 秒，媒体 `ended=true`、`paused=true`、无解码错误。对应原生 App 在 16:18:42 的后台播放线程发生 `SIGSEGV / art::JNI::CallVoidMethodV`。浏览器直播 `ended` 分支直接返回，手动续播又从同一个有限缓冲开始，形成重复旧片段。

本地 APK 的注册代码为直播回调指定 `TimeShiftPlayActivity`，点播使用 `VodPlayActivity`。原实现给直播传入了仅实现接口的动态 DEX 对象，不能安全替代原生缓存的类/方法对应关系。现在直播和点播分别创建并保留匹配的原生 Activity 回调，阻止后台实例执行未初始化的界面操作。浏览器直播 EOF 会重新请求当前频道；明确的用户暂停仍保留，手动续播不会重复已结束的缓存。

此前还实际观察到 QEMU 的多个视频 UDP 对端命中 Clash 默认规则，经代理节点出站；国内 peer 同时有 DIRECT 连接。规则与旧备份一致，不能据此把现象归因于 Clash Verge 升级本身。

## 直连方式

使用项目可选的 macOS socket 网卡绑定，物理网卡为本机 `en1`。局域网服务地址不变，只重启本项目 Node 服务和模拟器。加载范围通过子进程环境限定到本项目模拟器，不注入 Clash 或其他应用。

先做了一次受控原生搜索：两个 UDP socket 绑定物理网卡后，收到约 1.84 MB 数据，搜索约 2.28 秒返回。测试结束恢复了这些临时 socket 的绑定设置。这个样本证明协议可用，不是同查询的前后性能对照。

随后使用正式的项目直连模块冷启动模拟器，确认动态库实际加载、socket 的 `IP_BOUND_IF` 为 `en1` 的接口索引，并观察到绑定 socket 收到真实视频。同期只读查询 Clash 连接，没有发现 QEMU 流量被捕获。没有仅凭“面板里没有连接”下结论。

## 实播结果

| 检查 | 观察结果 |
| --- | --- |
| Golf HD 直播 | 原生取流首包约 1.78 秒；浏览器连续播放至 173 秒，`readyState=4`、无媒体错误，当前位置之后约 13.7 秒连续缓冲 |
| Golf HD 实际对端 | 绑定网卡的 socket 从国内和境外 peer 收到视频，约 6 秒采样收取 5.3 MB；这是传输数据量，不等于可用视频吞吐 |
| Silo S3E8 电视点播 | 原生首包约 1.83 秒；16 秒服务端输出采样约 1,636 KiB/s，缓冲由约 9 秒增长到约 40 秒 |
| Silo 视频出口 | 绑定 socket 从 `64.62.198.101:3113`、`64.62.198.102:3113` 收到视频，Clash 同期没有 QEMU 连接 |
| 未缓冲进度跳转 | 页面跳到约 6:42，随后正常播放到约 7:58，`readyState=4`，连续缓冲约 103 秒；此次没有密集采样首帧，因此不报告精确等待时间 |
| 直播 EOF 恢复 | 在切换直连模式前，受控结束服务端流后，浏览器耗尽旧缓冲并自动建立新会话，服务端新首包约 1.99 秒；没有手动重新选台 |

直连不等于所有片源都达到电视的速度。上述是有限样本，不能证明全片、所有节目、十分钟暂停续播都不缓冲。本轮没有把原生设备流量计数、服务端输出、文件写入和浏览器连续缓冲混作同一个指标，也没有用不同片源的结果计算“提速倍数”。
